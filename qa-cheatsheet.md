# QA Automation — Шпаргалка

Краткий рабочий конспект по обучению QA → QA Automation.

## 1. SDLC — Software Development Life Cycle

**SDLC** — жизненный цикл разработки программного обеспечения.

`Идея → Требования → Проектирование → Разработка → Тестирование → Релиз → Поддержка`

Этапы могут пересекаться и повторяться; тестирование происходит на разных этапах SDLC.

- **SRS (Software Requirements Specification)** — документ с требованиями к ПО.
- **UAT (User Acceptance Testing)** — проверка продукта с точки зрения принятия пользователем/заказчиком.
- **Production / Prod** — рабочая среда.

## 2. STLC — Software Testing Life Cycle

**STLC** — жизненный цикл процесса тестирования.

`Requirement Analysis → Test Planning → Test Case Development → Test Environment Setup → Test Execution → Test Cycle Closure`

**SDLC** — жизненный цикл всего продукта; **STLC** — жизненный цикл тестирования.

## 3. 7 принципов тестирования

1. **Testing shows presence of defects** — тестирование показывает наличие дефектов, но не доказывает их отсутствие.
2. **Exhaustive testing is impossible** — невозможно проверить все комбинации.
3. **Early testing** — раннее обнаружение дефектов дешевле и проще.
4. **Defect clustering** — дефекты часто концентрируются в небольшом числе областей.
5. **Pesticide paradox** — одни и те же тесты со временем перестают находить новые дефекты.
6. **Testing is context dependent** — тестирование зависит от продукта, требований и рисков.
7. **Absence-of-errors fallacy** — отсутствие найденных ошибок не означает автоматически хорошее качество продукта.

## 4. QA / QC / Testing

**QA (Quality Assurance)** — обеспечение качества; фокус на процессе и предотвращении проблем.

`QA = process + prevention`

**QC (Quality Control)** — контроль качества; фокус на продукте/результате.

`QC = product + control`

**Testing** — непосредственные проверки продукта для оценки качества и выявления дефектов.

В модели курса: `Testing ⊂ QC`.

## 5. Уровни тестирования и Test Pyramid

`Unit / Component → Integration → System → Acceptance`

- **Unit / Component** — отдельная часть системы.
- **Integration** — взаимодействие нескольких частей.
- **System** — система целиком.
- **Acceptance** — соответствие требованиям / пользовательские сценарии.
- **E2E (End-to-End)** — сквозной сценарий от начала до конца.

Общий принцип Test Pyramid: нижние уровни обычно быстрее и многочисленнее, верхние — сложнее, медленнее и дороже.

## 6. Unit / Component Testing

**Unit testing** — тестирование одного логически выделенного и изолированного элемента: функции, метода, класса и т. п.

**Component testing** — тестирование отдельного компонента без интеграции с другими компонентами.

Термины `unit`, `module`, `component` могут трактоваться по-разному; для практики особенно важен unit testing.

## 7. Integration Testing

**Integration testing** — проверка взаимодействия компонентов или систем.

- **CIT** — Component Integration Testing.
- **SIT** — System Integration Testing; в материале также отмечается вариант трактовки как интеграции отдельных систем, например через API.
- **Big Bang** — модули собираются вместе, затем тестируется интеграция.
- **Incremental** — модули добавляются и тестируются постепенно.
- **Top-Down** — сверху вниз; используются **stubs**.
- **Bottom-Up** — снизу вверх; используются **drivers**.
- **Sandwich / Hybrid / Bi-Directional** — комбинация подходов.

## 8. Positive / Negative / Destructive Testing

**Positive** → валидные данные и штатный сценарий.

**Negative** → невалидные данные и некорректные действия.

**Destructive** → намеренно нарушаем работоспособность, чтобы найти точку отказа; в материале рассматривается как форма негативного тестирования.

По материалу курса: сначала проверяется positive-сценарий; positive и negative проверки лучше разделять.

## 9. Smoke / Critical Path / Extended Testing

**Smoke testing** — самая важная ключевая функциональность; часто выполняется на новой build.

**Critical Path Testing** — важные типичные пользовательские сценарии, особенно новые/изменённые функции по материалу курса.

**Extended Testing** — более полный охват функциональности, включая редкие/экзотические сценарии.

## 10. Retest / Regression

**Retest** → проверяем, что конкретный исправленный дефект действительно исправлен.

**Regression** → проверяем, что изменения не сломали существующую или связанную функциональность.

По материалу курса:

`Fix → Retest → Regression`

Регрессионный набор выбирают с учётом изменённых областей, приоритетов и концентрации дефектов. Автоматизация помогает экономить время на повторных проверках.

## 11. Black / Gray / White-box

**Black-box** → внутреннее устройство не требуется; проверяем внешнее поведение.

**Gray-box** → частичное знание внутреннего устройства.

**White-box** → известно внутреннее устройство/код.

## 12. Functional / Non-functional

**Functional testing** → проверяем, **что** система делает: функции и поведение согласно требованиям.

**Non-functional testing** → проверяем другие характеристики качества: производительность, удобство, безопасность, совместимость и т. п.

Коротко:

`Functional → что делает?`

`Non-functional → насколько хорошо / удобно / безопасно / стабильно это работает?`

## 13. Manual / Automated

**Manual testing** — тесты выполняет человек без автоматизации проверки.

**Automated testing / Test automation** — часть проверок выполняется программой; человек разрабатывает и поддерживает автоматизацию.

Не всё целесообразно или возможно автоматизировать.

## 14. Static / Dynamic

**Static testing** — тестируемый компонент не выполняется: документы, требования, прототипы, code review, static analysis и т. п.

**Dynamic testing** — проверяем систему во время её выполнения.

## 15. Формализация тестирования

`Scripted → Exploratory → Ad hoc`

- **Scripted / test case based** — заранее подготовленные тест-кейсы и документация.
- **Exploratory** — сценарий частично определён, тестировщик одновременно изучает продукт и уточняет проверки.- **Ad hoc** — неформальная проверка без заранее подготовленных тест-кейсов/чек-листов.

## 16. Installation Testing

**Installation testing** — тестирование дефектов, связанных с установкой продукта.

Проверяем:

`Install → Uninstall → Update → Rollback → Retry after error → Automated installation → Component installation`

## 17. Usability Testing

**Usability testing** — исследование того, насколько конечному пользователю понятно, удобно и приятно работать с продуктом.

По материалу курса рассматриваются: **understandability, learnability, operability, attractiveness**, а также доступность, скорость/производительность, навигация и интерфейс, плавность.

**Usability → нефункциональное тестирование.**

## 18. Accessibility Testing (A11Y)

**Accessibility testing** — проверка пригодности продукта для людей с ограниченными возможностями.

Примеры:
- вспомогательные технологии: screen readers, speech recognition, экранная клавиатура, лупа;
- использование приложения одной рукой;
- специальные настройки цветопередачи;
- понятные инструкции и руководство пользователя.

**Accessibility → нефункциональное тестирование.**

Инструменты из материала: WAVE, TAV, Accessibility Valet, Accessibility Developer Tools.

## 19. Security Testing

**Security testing** — проверка способности приложения противостоять несанкционированному доступу к данным или функциям.

Примеры угроз из материала:
- SQL Injection;
- XSS;
- перехват трафика;
- brute force.

**Security → нефункциональное тестирование.**

**OWASP Top 10** — ориентир со значимыми категориями веб-уязвимостей и рекомендациями по защите/тестированию.

## 20. Internationalization / Localization

**Internationalization testing (i18n)** — проверка готовности продукта к работе с различными языками и национальными/культурными особенностями.

**Localization testing (l10n)** — проверка корректности адаптации продукта под конкретный язык и национальные/культурные особенности.

Коротко:

`i18n → готовность к международности`

`l10n → адаптация под конкретную локаль`

Оба относятся к **нефункциональному тестированию**.

## 21. Compatibility Testing

**Compatibility testing** — проверка способности приложения работать в указанном окружении.

Подвиды из материала:

- **Configuration testing** → аппаратная платформа, ОС, сетевая инфраструктура.
- **Cross-browser testing** → разные браузеры и их версии.
- **Cross-platform testing** → разные операционные системы.

**Compatibility → нефункциональное тестирование.**

## 22. Reliability / Recoverability / Failover

**Reliability testing** → способность приложения выполнять функции в заданных условиях в течение заданного времени или количества операций.

`Reliability → стабильно работает долго?`

**Recoverability testing** → способность восстановить функции, заданный уровень производительности и данные после критической ситуации с временной/частичной потерей работоспособности.

`Recoverability → после сбоя сможет восстановиться?`

**Failover testing** → создание/эмуляция критической ситуации для проверки механизмов, предотвращающих нарушение работоспособности, производительности и повреждение данных.

`Failover → при сбое срабатывает предусмотренный механизм?`

Все три относятся к **нефункциональному тестированию**.

## 23. Performance Testing

**Performance testing** — исследование показателей скорости реакции приложения при различной по характеру и интенсивности нагрузке.

Все виды ниже относятся к **нефункциональному тестированию**.

### Load testing
Проверяем способность сохранять заданные показатели качества при допустимой нагрузке и некотором её превышении; определяем запас прочности.

`Load → допустимая нагрузка + запас`

### Scalability testing
Проверяем способность увеличивать показатели производительности в соответствии с увеличением доступных ресурсов.

`Scalability → увеличиваем ресурсы → смотрим рост производительности`

### Volume testing
Проверяем производительность при обработке больших объёмов данных.

`Volume → большой объём данных`

### Stress testing
Проверяем поведение при нагрузке, значительно превышающей расчётную, либо при недоступности значительной части необходимых ресурсов.

`Stress → сильная перегрузка`

### Concurrency testing
Проверяем поведение при большом количестве одновременно поступающих запросов, конкурирующих за ресурсы: БД, память, сеть, диск и т. д.

`Concurrency → много одновременных запросов`

### Быстрая шпаргалка

| Тип | Главная идея |
|---|---|
| Load | допустимая нагрузка и запас |
| Scalability | увеличение доступных ресурсов |
| Volume | большой объём данных |
| Stress | сильное превышение расчётной нагрузки |
| Concurrency | одновременные запросы и конкуренция за ресурсы |

## 24. Модель качества

В материале со ссылкой на **ГОСТ Р ИСО/МЭК 25010—2015** показаны характеристики качества программной продукции:

- функциональная пригодность;
- уровень производительности;
- совместимость;
- удобство использования;
- надёжность;
- защищённость;
- сопровождаемость;
- переносимость.

Для текущего этапа достаточно понимать связь характеристик с соответствующими видами нефункционального тестирования.

## 25. Свойства качественных требований

Качественное требование должно быть понятным, реализуемым и пригодным для объективной проверки.

- **Completeness (завершённость)** — содержит всю необходимую информацию; ничего важного не оставлено в стиле «это и так понятно».
- **Atomicity (атомарность / единичность)** — описывает одну ситуацию и не объединяет несколько независимых требований.
- **Consistency (непротиворечивость / последовательность)** — не противоречит самому себе, другим требованиям и связанным документам.
- **Unambiguousness / Clearness (недвусмысленность / ясность)** — допускает однозначное объективное понимание; без расплывчатых формулировок, непонятного жаргона и неоднозначных сокращений.
- **Feasibility (выполнимость)** — технически реализуемо и укладывается в ограничения проекта по бюджету и срокам.
- **Obligatoriness + Up-to-date (обязательность и актуальность)** — требование действительно нужно проекту, имеет корректный приоритет и не устарело.
- **Traceability (прослеживаемость)** — требование можно связать с другими уровнями требований, а также с тест-планом, тест-кейсами, архитектурными решениями и т. д.
  - **Vertical traceability** — связь требований разных уровней.
  - **Horizontal traceability** — связь требования с артефактами разработки и тестирования.
- **Modifiability (модифицируемость)** — отдельные требования и набор требований можно относительно легко изменять без появления новых противоречий и потери связности.
- **Ranked for importance, stability, priority** — требования имеют понятные оценки/приоритеты по:
  - важности — насколько успех проекта зависит от реализации;
  - стабильности — насколько вероятны изменения;
  - срочности — когда нужно направить на него усилия команды.
- **Correctness (корректность)** — требование соответствует ожидаемому поведению/целям и не содержит ошибок.
- **Verifiability (проверяемость)** — можно создать объективный тест-кейс или набор тест-кейсов, однозначно показывающих соответствие реализации требованию.

> **Для текущего этапа:** свойства не нужно заучивать списком. Важно понимать общую идею: хорошее требование должно быть полным, атомарным, непротиворечивым, однозначным, реализуемым и проверяемым.


## 26. Документирование требований

### Use Case

**Use case** — сценарий взаимодействия пользователя (или пользователей) с программным продуктом для достижения конкретной цели.

На **use case diagram**:
- **Actor** — пользователь/роль, взаимодействующая с системой;
- **System** — сама система;
- **Use case** — функция/вариант использования.

Для QA use case полезен как описание пользовательского сценария, который можно проверять.

### User Story

**User story** — общее описание функции программы, написанное от имени пользователя.

Шаблон:

`As a [persona], I [want to], [so that]`

или:

> «Как [тип пользователя], я хочу [действие], чтобы [цель]».

В user story обязательно учитываются **acceptance criteria (критерии готовности)** — конкретные требования к разрабатываемой функции.

Для QA именно acceptance criteria часто становятся непосредственной основой для проверок.

### Mockup

**Mockup (макет)** — реалистичная модель приложения, показывающая, как должен выглядеть frontend.

В тестировании макет используется как ориентир для проверки:
- наличия элементов;
- их размера;
- стиля;
- поведения.

### Быстрая разница

`Use Case → сценарий взаимодействия`

`User Story → функция с точки зрения пользователя + acceptance criteria`

`Mockup → как должен выглядеть и вести себя интерфейс`

> **Для текущего этапа:** эти три понятия стоит узнавать и различать. Особенно важны **User Story + Acceptance Criteria**, потому что из них удобно переходить к тестированию конкретной функции.


## 27. Работа тестировщика с требованиями

### Идеальный процесс

1. Бизнес-аналитики или Product Owner создают требования; обычно они включают дизайнерские макеты.
2. QA получает требования и проверяет их на соответствие свойствам качественных требований.
3. В Scrum требования дополнительно обсуждаются и уточняются командой на **Backlog Refinement**.
4. Найденные неточности возвращаются на доработку; цикл анализа и уточнений повторяется до устранения проблем.
5. После согласования требований они идут в разработку, а QA заранее создаёт тестовую документацию.
6. **Test cases / checklists желательно создавать до разработки функциональности** — это пример **Shift Left Testing / Early Testing**.
7. После начала спринта изменения требований обычно не приветствуются.

### Неидеальный процесс

На практике возможны отклонения:
- требования уточняются уже во время разработки;
- тестовая документация создаётся после реализации;
- требования вообще не документируются и существуют только в неявном виде.

> **Главная идея для QA:** не ждать готовую функциональность, чтобы начать думать о тестировании. Требования нужно анализировать заранее и использовать их как основу для будущих проверок.


## 28. Scrum

**Scrum** — лёгкий фреймворк, который помогает людям, командам и организациям создавать ценность с помощью адаптивных решений комплексных проблем.

### 28.1. Ценности Scrum

Пять ценностей:

- **Commitment / Приверженность** — команда привержена своим целям и поддержке друг друга.
- **Focus / Сфокусированность** — основной фокус в Sprint на прогрессе к цели.
- **Openness / Открытость** — открыто обсуждаем работу и вызовы.
- **Respect / Уважение** — участники уважают друг друга как профессионалов.
- **Courage / Смелость** — готовы поступать правильно и решать сложные проблемы.

Для практики достаточно знать название и общий смысл ценностей; дословно Scrum Guide их не заучиваем.

### 28.2. Scrum Team и роли

**Scrum Team** — небольшая команда, без подкоманд и иерархий внутри. Она кросс-функциональная и самоуправляемая.

- **Cross-functional** — в команде есть все необходимые навыки для создания ценности.
- **Self-managing** — команда сама решает, кто, что, когда и как делает.
- Команда сфокусирована на **Product Goal**.

Scrum Team состоит из:

#### Developers
**Developers** — участники Scrum Team, создающие готовый к использованию **Increment**.

Developers отвечают за:
- создание плана Sprint — **Sprint Backlog**;
- качество и соблюдение **Definition of Done**;
- ежедневную адаптацию плана для достижения **Sprint Goal**;
- взаимную подотчётность.

В терминологии Scrum **QA/AQA относится к Developers**, а не является отдельной четвёртой ролью.

#### Product Owner (PO)

**PO** отвечает за максимизацию ценности продукта и эффективное управление **Product Backlog**.

Ключевые обязанности:
- формулировать и коммуницировать **Product Goal**;
- создавать и объяснять элементы Product Backlog;
- упорядочивать Product Backlog;
- обеспечивать его прозрачность, доступность и понимание.

Коротко:

`PO → что и зачем важно для продукта`

#### Scrum Master (SM)

**Scrum Master** отвечает за применение Scrum и помогает команде и организации понимать и применять его теорию и практики.

Помогает:
- развивать самоуправление и кросс-функциональность;
- устранять препятствия;
- улучшать работу с Product Backlog;
- фасилитировать взаимодействие со stakeholders.

**Scrum Master ≠ начальник команды.**

### 28.3. Sprint

**Sprint** — контейнер для остальных Scrum-событий и фиксированный период продолжительностью не более одного месяца. Новый Sprint начинается сразу после предыдущего.

В Sprint:
- не вносят изменения, которые ставят под угрозу **Sprint Goal**;
- качество не снижается;
- Product Backlog уточняется;
- содержание работы может уточняться при появлении новых знаний.

Упрощённо:

`Sprint → Planning → работа + Daily → Review → Retrospective → следующий Sprint`

### 28.4. Scrum Events

#### Sprint Planning

Начинает Sprint.

Три главных вопроса:

- **Why?** — зачем этот Sprint? → **Sprint Goal**
- **What?** — что можно сделать?
- **How?** — как выполнить выбранную работу?

Для месячного Sprint максимум — **8 часов**; для более короткого Sprint обычно меньше.

#### Daily Scrum

**15 минут**, предназначен для Developers.

Цель — инспекция прогресса к **Sprint Goal** и адаптация **Sprint Backlog**.

Распространённый формат из трёх вопросов:
- что сделал вчера;
- что сделаю сегодня;
- есть ли препятствия.

В Scrum Guide 2020 эти три вопроса не являются обязательным форматом Daily Scrum.

#### Sprint Review

Цель — инспекция результата Sprint и выявление возможностей для адаптации.

Scrum Team и stakeholders обсуждают:
- что достигнуто;
- что изменилось;
- что делать дальше;
- нужно ли изменить Product Backlog.

**Sprint Review — рабочая сессия, а не просто презентация.**

Для месячного Sprint максимум — **4 часа**.

#### Sprint Retrospective

Цель — запланировать повышение **качества и эффективности**.

Команда обсуждает:
- что прошло хорошо;
- какие проблемы возникли;
- что можно улучшить;
- какие изменения внедрить.

Наиболее полезные улучшения могут попасть в Sprint Backlog следующего Sprint.

Для месячного Sprint максимум — **3 часа**.

### 28.5. Scrum Artifacts

#### Product Backlog

**Product Backlog** — упорядоченный и постоянно обновляемый список того, что необходимо для улучшения продукта.

Это единственный источник работы Scrum Team.

**Product Backlog Refinement** — процесс разбиения и дальнейшего уточнения элементов Product Backlog, чтобы они стали более понятными и конкретными.

Refinement — важная рабочая деятельность, но **не отдельное официальное событие Scrum**.

#### Sprint Backlog

Состоит из:

`WHY + WHAT + HOW`

- **WHY** → Sprint Goal;
- **WHAT** → выбранные элементы Product Backlog;
- **HOW** → осуществимый план действий.

Sprint Backlog — план Developers для самих Developers и наглядная картина работы текущего Sprint.

Он может обновляться в течение Sprint по мере появления новых знаний.

#### Increment

**Increment** — конкретная ступенька к достижению Product Goal.

Каждый Increment дополняет предыдущие и должен быть **пригодным для использования (usable)**.

В одном Sprint может быть несколько Increments. Increment может быть поставлен stakeholders до окончания Sprint; Sprint Review не является единственным моментом поставки ценности.

### 28.6. Estimation

**Estimation** — прогнозирование усилий, необходимых для выполнения элемента Product Backlog.

Часто используются **Story Points** — относительные единицы оценки.

Story Points:

- не равны часам;
- позволяют сравнивать относительный размер/сложность работы;
- часто используют последовательность **1, 2, 3, 5, 8, 13...**.
**Planning Poker** — распространённая техника коллективной оценки:

`задача → индивидуальные оценки → обсуждение расхождений → общая оценка`

Оценка часто проводится во время **Refinement**.

> Story Points, Fibonacci и Planning Poker — распространённые практики оценки, а не обязательные элементы Scrum Guide.

### 28.7. Velocity и Capacity

В модели курса:

**Velocity / Скорость** — количество работы, которое команда фактически завершила за Sprint.

Считается как сумма Story Points **полностью завершённых** элементов.

Пример:

`3 SP + 5 SP + 2 SP = Velocity 10 SP`

Незавершённые элементы в Velocity не входят.

**Capacity** — вместимость Sprint; в материале курса — количество Story Points, определённых для элементов Sprint Backlog.

Коротко:

`Capacity → сколько взяли/запланировали`

`Velocity → сколько полностью сделали`

> В реальных командах термин Capacity может использоваться шире, например для доступной рабочей способности команды с учётом людей и времени. Смысл зависит от принятого в команде подхода.

### 28.8. Дополнительные рабочие термины

#### MVP — Minimum Viable Product

**MVP** — минимально жизнеспособная версия продукта, позволяющая с минимальными затратами получить максимум информации и обратной связи от клиентов.

`минимальная версия → пользователи → feedback → новые решения`

#### Stakeholder

**Stakeholder** — заинтересованное лицо, которое может давать обратную связь по видению продукта, Product Backlog и Increments.

Stakeholders часто участвуют в **Sprint Review**.

#### Sprint Board / Scrum Board

Инструмент для визуализации работы Sprint.

Типичный вариант:

`To Do → In Progress → Done`

В реальной команде колонок может быть больше, например:

`Ready for Dev → In Development → Ready for QA → Testing → Bug → Done`

### 28.9. Практическая картина двухнедельного Sprint

Пример рабочего цикла:

`Sprint Planning → Daily + работа → Refinement → Daily + работа → Review → Retrospective`

При этом:
- **Daily** — каждый рабочий день;
- **Refinement** может проходить регулярно по мере необходимости;
- **Bug Triage** может проводиться для разбора и приоритизации накопившихся дефектов;
- **Demo** может использоваться для показа готовой функциональности stakeholders.

**Bug Triage** и отдельная **Demo** — не официальные события Scrum.

Для QA особенно важен Refinement: здесь можно заранее задавать вопросы по требованиям, граничным случаям, ошибкам, правам доступа, интеграциям и ожидаемому поведению.

### 28.10. Что важно различать

| Термин | Суть |
|---|---|
| Product Backlog | всё, что потенциально нужно продукту |
| Sprint Backlog | что делаем сейчас и как |
| Increment | готовый пригодный к использованию результат |
| Product Goal | долгосрочная цель продукта |
| Sprint Goal | цель текущего Sprint |
| Estimation | оценка усилий |
| Story Points | относительная единица оценки |
| Capacity | сколько запланировали в модели курса |
| Velocity | сколько полностью завершили |
| Refinement | уточнение Product Backlog |
| Sprint Review | инспекция результата + адаптация |
| Retrospective | улучшение процесса работы команды |
| Stakeholder | заинтересованное лицо |
| Sprint Board | визуализация текущей работы |
| MVP | минимальная версия для получения feedback |

> **Главный mental model:** Scrum — это не набор митингов. Команда работает короткими циклами, создаёт usable Increment, получает обратную связь, инспектирует результат и адаптирует дальнейшую работу.
## 29. Эквивалентное разбиение (Equivalence Partitioning)

**Эквивалентное разбиение (EP)** — деление входных данных на классы, внутри которых система должна обрабатывать значения одинаковым образом и получать одинаковый результат.

**Класс эквивалентности** — набор данных, обрабатываемых одинаково и приводящих к одинаковому результату.

### Как применять

1. Определить классы эквивалентности.
2. Выделить позитивные и негативные классы.
3. Взять хотя бы одного представителя из каждого класса.
4. При необходимости добавить отдельные невалидные классы для неправильного формата.

Пример: поле количества товара принимает целое число от `1` до `10` включительно.

| Класс | Примеры | Ожидаемый результат |
|---|---|---|
| Позитивный | 1–10 | значение принимается |
| Негативный | 0, 11, -5 | ошибка |
| Невалидный формат | abc, спецсимволы | ошибка |
| Невалидный формат | 2.5 | ошибка, если разрешены только целые числа |

Главная идея:

> Не нужно проверять все значения класса. Достаточно выбрать представителя класса, потому что предполагается, что правила обработки применяются ко всему классу одинаково.

Дополнительные классы стоит выделять, если система может обрабатывать их иначе. Например, отрицательное число и строка из букв могут обе приводить к ошибке, но относятся к разным типам невалидного ввода.

## 30. Анализ граничных значений (Boundary Value Analysis)

**Анализ граничных значений (BVA)** — продолжение эквивалентного разбиения. Некорректное поведение вероятнее на границах класса, чем внутри него.

В материале курса BVA применяется к классам, состоящим из **упорядоченных числовых значений**.

**Граничное значение** — значение на границе класса.

Для диапазона `1–10` границы:

- нижняя → `1`;
- верхняя → `10`.

### Метод 1

Проверяем:

- нижнюю границу и значение до неё;
- верхнюю границу и значение после неё.

Получаем:

`0, 1, 10, 11`
### Метод 2

Проверяем:

- нижнюю границу и значения до и после неё;
- верхнюю границу и значения до и после неё.

Получаем:

`0, 1, 2, 9, 10, 11`

Именно **метод 2** использовался в практическом примере выше.

> В материале отмечается, что в сообществе существуют споры о том, какой вариант считать правильным. При выполнении тестового задания полезно явно указать, какой метод BVA используется.

### EP + BVA

Эти техники хорошо работают вместе:

`EP → определяем классы`

`BVA → проверяем границы этих классов`

Например, для возраста:

- `0–17` → 50%;
- `18–54` → 25%;
- `55+` → 75%;
- `<0` → ошибка.

При BVA особенно интересны значения вокруг границ: `-1, 0, 1, 16, 17, 18, 53, 54, 55, 56`.

> Полученные наборы значений можно использовать как основу для чек-листов и тест-кейсов.

## 31. Попарное тестирование (Pairwise Testing)

**Попарное тестирование (Pairwise Testing)** — техника тестирования методом чёрного ящика, при которой тестовые сценарии строятся так, чтобы проверить все комбинации пар **параметр–значение**.

Главная идея:

> Когда полная комбинация параметров даёт слишком много тестов, вместо полного перебора покрываем взаимодействия всех пар параметров и их значений.

### Пример

Фильтр интернет-магазина:

| Параметр | Значения |
|---|---|
| Цвет | красный, белый, чёрный, серый |
| Размер | S, M, L, XL |
| Пол | мужской, женский, унисекс |
| Доставка | есть, нет |

Полный перебор:

`4 × 4 × 3 × 2 = 96` комбинаций.

С помощью Pairwise количество тестов в примере курса сокращается до **16**, при этом таблица строится так, чтобы покрыть пары параметров и их значений.

### Подходы

Для формирования пар в материале рассматриваются:

- **Ортогональные массивы (Orthogonal Arrays)**;
- **All Pairs**.

Для практики курса основной акцент — **All Pairs**, который автоматически генерирует необходимые пары.

**PICT** — один из популярных инструментов для генерации Pairwise-наборов.

### Практический алгоритм

1. Определить параметры тестируемой функции.
2. Выписать все возможные значения каждого параметра.
3. Начать с параметра, у которого больше всего значений.
4. Передать параметры и значения в Pairwise / All Pairs генератор.
5. Полученную таблицу использовать для создания **чек-листа или тест-кейсов**.

### Что важно запомнить

`Полный перебор → слишком много комбинаций`

`Pairwise → сокращаем количество тестов → покрываем пары параметров и значений`

Не нужно запоминать вручную построение больших Pairwise-таблиц. В реальной практике для генерации таких наборов используются специальные инструменты.


## 32. Таблица принятия решений (Decision Table Testing)

**Таблица принятия решений** (также **таблица альтернатив**) — техника для записи сложных бизнес-правил. Тестировщик определяет **условия (входы)** и **действия / результаты (выходы)**.

Условия указываются сверху, действия — снизу. Каждая колонка представляет отдельное **правило (Rule)**, то есть конкретную комбинацию условий и соответствующий результат.

### Пример

Для расчёта оклада и премии сотрудника:

|  | R1 | R2 | R3 | R4 |
|---|---|---|---|---|
| **Есть опыт?** | Нет | Нет | Да | Да |
| **Есть высшее образование?** | Нет | Да | Нет | Да |
| **Оклад** | 500 | 600 | 600 | 700 |
| **Премия** | 5% | 10% | 15% | 20% |

Каждая колонка — отдельное правило, которое можно использовать как основу для тест-кейса.

### Что важно запомнить

> **Decision Table = комбинация условий → ожидаемое действие / результат.**

Техника особенно полезна, когда результат зависит не от одного условия, а от их сочетания.

## 33. Тестирование состояний и переходов (State Transition Testing)

**State Transition Testing** — разработка тестов методом чёрного ящика на основе модели переходов состояний.

Модель описывает поведение **одного объекта** и включает:

- **State (состояние)** — состояние, в котором система ожидает возникновения одного или нескольких событий;
- **Transition (переход)** — изменение состояния из одного в другое;
- **Event (событие)** — то, что вызывает изменение состояния;
- **Action (действие)** — операция, вызванная изменением состояния;
- **Entry point (входная точка)** — начальная точка модели.

### Пример

Карточка товара в интернет-магазине:

`Товар не существует → создать → Товар существует`

Из состояния **«Товар существует»** можно, например:

- изменить → остаться в состоянии «Товар существует»;
- удалить → перейти в состояние «Товар не существует».

Ещё один простой пример:

`Создан → Оплачен → Отправлен → Доставлен`

Здесь оплата заказа является **событием**, которое переводит заказ из состояния **«Создан»** в состояние **«Оплачен»**.

### Что важно запомнить

> **State Transition = текущее состояние → событие → переход → новое состояние.**

Главная идея — проверять не только отдельное действие, но и то, **что происходит с объектом в зависимости от его текущего состояния**.
