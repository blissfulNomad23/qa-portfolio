# QA Automation — Шпаргалка

Краткий рабочий конспект по обучению QA → QA Automation.

## 1. SDLC — Software Development Life Cycle

**SDLC** — жизненный цикл разработки программного обеспечения.

Типовая схема:

`Идея → Требования → Проектирование → Разработка → Тестирование → Релиз → Поддержка`

Важно:
- этапы не обязательно идут строго линейно;
- могут пересекаться и повторяться;
- тестирование может происходить на разных этапах SDLC.

Ключевые термины:
- **SRS (Software Requirements Specification)** — документ с требованиями к ПО.
- **UAT (User Acceptance Testing)** — проверка продукта с точки зрения принятия пользователем/заказчиком.
- **Production / Prod** — рабочая среда, где используется реальный продукт.

## 2. STLC — Software Testing Life Cycle

**STLC** — жизненный цикл процесса тестирования.

Основные этапы:

`Requirement Analysis → Test Planning → Test Case Development → Test Environment Setup → Test Execution → Test Cycle Closure`

Разница:
- **SDLC** — жизненный цикл всего продукта.
- **STLC** — жизненный цикл тестирования.
- Они пересекаются во времени.

## 3. 7 принципов тестирования

### 1. Testing shows presence of defects
Тестирование может показать наличие дефектов, но не доказать их отсутствие.

### 2. Exhaustive testing is impossible
Невозможно проверить все комбинации данных, действий, окружений и состояний системы.

Поэтому выбирают важные и рискованные сценарии и используют техники тест-дизайна.

### 3. Early testing
Чем раньше обнаружен дефект, тем проще и дешевле его исправить.

### 4. Defect clustering
Дефекты часто концентрируются в небольшом количестве компонентов или областей системы.

### 5. Pesticide paradox
Если постоянно выполнять одни и те же тесты, со временем они перестают находить новые дефекты.

Тесты нужно пересматривать, обновлять и дополнять.

### 6. Testing is context dependent
Тестирование зависит от конкретного продукта, его требований, рисков и контекста.

### 7. Absence-of-errors fallacy
Отсутствие найденных ошибок не означает автоматически, что продукт хороший или полезный.

## 4. QA / QC / Testing

### QA — Quality Assurance
**Обеспечение качества.**

Фокус: **процесс**.

QA направлено на обеспечение выполнения требований к качеству и предотвращение проблем.

`QA = process + prevention`

### QC — Quality Control
**Контроль качества.**

Фокус: **продукт / результат**.

QC включает действия по оценке качества компонента или системы.

`QC = product + control`

### Testing
**Тестирование** — конкретные проверки программного продукта/системы для оценки качества и выявления дефектов.

В рассматриваемой модели:

`Testing ⊂ QC`

То есть тестирование является частью контроля качества.

### Главное различие

| | QA | QC | Testing |
|---|---|---|---|
| Фокус | Процесс | Продукт | Проверки продукта |
| Основная идея | Предотвращать проблемы | Контролировать результат | Находить дефекты / проверять соответствие |

**QA → предотвращаем**

**QC → контролируем результат**

**Testing → непосредственно проверяем**

## 5. Уровни тестирования и Test Pyramid

**Пирамида тестирования (Test Pyramid)** — метафора для группировки динамических тестов по уровням и представления о том, сколько тестов обычно должно быть на каждом уровне.

Основной принцип из курса: тест должен быть примерно на том же уровне, что и **тестируемый объект**. Проверки более высокого уровня не должны заново покрывать всю условную логику и все пограничные случаи, которые уже проверяются на более низком уровне.

### Уровни

`Unit / Component → Integration → System → Acceptance`

- **Unit / Component / Module testing** — проверяется минимально-атомарный модуль программы, чаще всего одна функция или метод. Таких тестов должно быть больше всего.
- **Integration testing** — несколько модулей программы проверяются вместе.
- **System testing** — проверяется программа целиком.
- **Acceptance testing (AT)** — программа принимается заказчиком на соответствие заявленным требованиям либо проверяются сценарии с точки зрения пользователя.

### E2E — End-to-End testing
**End-to-End (сквозное) тестирование** — проверка сценария от начала до конца, включая взаимодействие с внешними интерфейсами.

Пример из курса для интернет-магазина:
`Регистрация → выбор товара → оформление заказа → покупка`

**Важно:** в контексте рассматриваемой в курсе пирамиды уровень UAT/Acceptance представлен через E2E-тесты. Не нужно пока заучивать это как универсальное правило для всех моделей тестирования.

### Что запомнить сейчас

`Unit` → одна маленькая часть

`Integration` → несколько частей вместе

`System` → вся система

`Acceptance / E2E` → сценарий с точки зрения пользователя / принятие продукта

Общий принцип пирамиды: **чем ниже уровень, тем тесты обычно быстрее и их больше; чем выше — тем проверки обычно сложнее, медленнее и дороже.**

## 6. Unit / Component Testing

### Unit testing — модульное / юнит-тестирование
**Unit testing** используется для тестирования одного логически выделенного и изолированного элемента системы: отдельной функции, метода класса, класса, процедуры и т.п.

Пример:

```python
def calculate_total(price, tax):
    return price + price * tax
```

Такую функцию можно тестировать отдельно, не проверяя при этом весь сайт, API или базу данных.

### Component testing — компонентное тестирование
**Component testing** — тестирование отдельных аппаратных или программных компонентов системы. В контексте материала курса компонент тестируется отдельно, без интеграции с другими компонентами.

### Терминология

Разные источники могут по-разному трактовать `unit`, `module` и `component`: где-то они используются почти как синонимы, где-то между ними проводят различия.

Для практики QA Automation особенно важно понимать **unit testing**, потому что с ним мы будем работать при автоматизации тестов на Python и `pytest`.

### Коротко

`Unit` → одна изолированная часть кода

`Component` → отдельный компонент без интеграции с другими компонентами

Не нужно сейчас заучивать тонкие различия терминов из разных источников.

## 7. Integration Testing

**Integration testing (интеграционное тестирование)** — уровень тестирования, который фокусируется на взаимодействии между компонентами или системами.

### Уровни интеграционного тестирования

- **CIT — Component Integration Testing** — проверяется взаимодействие между компонентами одной системы после компонентного тестирования.
- **SIT — System Integration Testing** — в рассматриваемом материале это тестирование системы, состоящей из множества подсистем.

Автор курса также отмечает другой вариант трактовки SIT: тестирование взаимодействия двух и более отдельных систем, например через **API (Application Programming Interface)**.

### Подходы к интеграционному тестированию

**Big Bang Approach**
- Все или почти все разработанные модули собираются вместе.
- Затем проводится интеграционное тестирование системы или её основной части.

**Incremental Approach**
- Сначала объединяют и тестируют два или более связанных модуля.
- Затем постепенно добавляют остальные модули и продолжают тестирование.

В рамках incremental approach:

- **Top-Down** — сначала тестируются высокоуровневые модули, затем постепенно добавляются низкоуровневые. Недостающие нижние модули временно заменяются **stubs (заглушками)**.
- **Bottom-Up** — сначала тестируются низкоуровневые модули и постепенно подключаются более высокоуровневые. Для имитации отсутствующих верхних модулей используются **drivers (драйверы)**.
- **Sandwich / Hybrid / Bi-Directional** — комбинация Top-Down и Bottom-Up; одновременно используются drivers и stubs для ещё не готовых частей.

### Что запомнить сейчас

`Unit` → одна часть

`Integration` → взаимодействие нескольких частей

`System` → вся система

`API` → один из типичных способов интеграции систем

Не нужно сейчас зубрить детали CIT/SIT, Big Bang, Sandwich и различия stubs/drivers до уровня экзамена. Достаточно понимать общий принцип и знать названия подходов.

## Как использовать шпаргалку

Не нужно заучивать формулировки дословно.

Цель:
1. объяснить термин своими словами;
2. привести простой пример;
3. отличить похожие понятия;
4. применить концепцию к реальному тестированию.

Новые темы добавляются сюда по мере прохождения обучения.
