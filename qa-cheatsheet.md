# QA Automation — Шпаргалка

Краткий рабочий конспект по обучению QA → QA Automation.

## 1. SDLC — Software Development Life Cycle

**SDLC** — жизненный цикл разработки программного обеспечения.

`Идея → Требования → Проектирование → Разработка → Тестирование → Релиз → Поддержка`

Этапы могут пересекаться и повторяться; тестирование происходит на разных этапах SDLC.

- **SRS (Software Requirements Specification)** — документ с требованиями к ПО.
- **UAT (User Acceptance Testing)** — проверка продукта с точки зрения принятия пользователем/заказчиком.
- **Production / Prod** — рабочая среда.

## 2. STLC — Software Testing Life Cycle

**STLC** — жизненный цикл процесса тестирования.

`Requirement Analysis → Test Planning → Test Case Development → Test Environment Setup → Test Execution → Test Cycle Closure`

**SDLC** — жизненный цикл всего продукта; **STLC** — жизненный цикл тестирования.

## 3. 7 принципов тестирования

1. **Testing shows presence of defects** — тестирование показывает наличие дефектов, но не доказывает их отсутствие.
2. **Exhaustive testing is impossible** — невозможно проверить все комбинации.
3. **Early testing** — раннее обнаружение дефектов дешевле и проще.
4. **Defect clustering** — дефекты часто концентрируются в небольшом числе областей.
5. **Pesticide paradox** — одни и те же тесты со временем перестают находить новые дефекты.
6. **Testing is context dependent** — тестирование зависит от продукта, требований и рисков.
7. **Absence-of-errors fallacy** — отсутствие найденных ошибок не означает автоматически хорошее качество продукта.

## 4. QA / QC / Testing

**QA (Quality Assurance)** — обеспечение качества; фокус на процессе и предотвращении проблем.

`QA = process + prevention`

**QC (Quality Control)** — контроль качества; фокус на продукте/результате.

`QC = product + control`

**Testing** — непосредственные проверки продукта для оценки качества и выявления дефектов.

В модели курса: `Testing ⊂ QC`.

## 5. Уровни тестирования и Test Pyramid

`Unit / Component → Integration → System → Acceptance`

- **Unit / Component** — отдельная часть системы.
- **Integration** — взаимодействие нескольких частей.
- **System** — система целиком.
- **Acceptance** — соответствие требованиям / пользовательские сценарии.
- **E2E (End-to-End)** — сквозной сценарий от начала до конца.

Общий принцип Test Pyramid: нижние уровни обычно быстрее и многочисленнее, верхние — сложнее, медленнее и дороже.

## 6. Unit / Component Testing

**Unit testing** — тестирование одного логически выделенного и изолированного элемента: функции, метода, класса и т. п.

**Component testing** — тестирование отдельного компонента без интеграции с другими компонентами.

Термины `unit`, `module`, `component` могут трактоваться по-разному; для практики особенно важен unit testing.

## 7. Integration Testing

**Integration testing** — проверка взаимодействия компонентов или систем.

- **CIT** — Component Integration Testing.
- **SIT** — System Integration Testing; в материале также отмечается вариант трактовки как интеграции отдельных систем, например через API.
- **Big Bang** — модули собираются вместе, затем тестируется интеграция.
- **Incremental** — модули добавляются и тестируются постепенно.
- **Top-Down** — сверху вниз; используются **stubs**.
- **Bottom-Up** — снизу вверх; используются **drivers**.
- **Sandwich / Hybrid / Bi-Directional** — комбинация подходов.

## 8. Positive / Negative / Destructive Testing

**Positive** → валидные данные и штатный сценарий.

**Negative** → невалидные данные и некорректные действия.

**Destructive** → намеренно нарушаем работоспособность, чтобы найти точку отказа; в материале рассматривается как форма негативного тестирования.

По материалу курса: сначала проверяется positive-сценарий; positive и negative проверки лучше разделять.

## 9. Smoke / Critical Path / Extended Testing

**Smoke testing** — самая важная ключевая функциональность; часто выполняется на новой build.

**Critical Path Testing** — важные типичные пользовательские сценарии, особенно новые/изменённые функции по материалу курса.

**Extended Testing** — более полный охват функциональности, включая редкие/экзотические сценарии.

## 10. Retest / Regression

**Retest** → проверяем, что конкретный исправленный дефект действительно исправлен.

**Regression** → проверяем, что изменения не сломали существующую или связанную функциональность.

По материалу курса:

`Fix → Retest → Regression`

Регрессионный набор выбирают с учётом изменённых областей, приоритетов и концентрации дефектов. Автоматизация помогает экономить время на повторных проверках.

## 11. Black / Gray / White-box

**Black-box** → внутреннее устройство не требуется; проверяем внешнее поведение.

**Gray-box** → частичное знание внутреннего устройства.

**White-box** → известно внутреннее устройство/код.

## 12. Functional / Non-functional

**Functional testing** → проверяем, **что** система делает: функции и поведение согласно требованиям.

**Non-functional testing** → проверяем другие характеристики качества: производительность, удобство, безопасность, совместимость и т. п.

Коротко:

`Functional → что делает?`

`Non-functional → насколько хорошо / удобно / безопасно / стабильно это работает?`

## 13. Manual / Automated

**Manual testing** — тесты выполняет человек без автоматизации проверки.

**Automated testing / Test automation** — часть проверок выполняется программой; человек разрабатывает и поддерживает автоматизацию.

Не всё целесообразно или возможно автоматизировать.

## 14. Static / Dynamic

**Static testing** — тестируемый компонент не выполняется: документы, требования, прототипы, code review, static analysis и т. п.

**Dynamic testing** — проверяем систему во время её выполнения.

## 15. Формализация тестирования

`Scripted → Exploratory → Ad hoc`

- **Scripted / test case based** — заранее подготовленные тест-кейсы и документация.
- **Exploratory** — сценарий частично определён, тестировщик одновременно изучает продукт и уточняет проверки.
- **Ad hoc** — неформальная проверка без заранее подготовленных тест-кейсов/чек-листов.

## 16. Installation Testing

**Installation testing** — тестирование дефектов, связанных с установкой продукта.

Проверяем:

`Install → Uninstall → Update → Rollback → Retry after error → Automated installation → Component installation`

## 17. Usability Testing

**Usability testing** — исследование того, насколько конечному пользователю понятно, удобно и приятно работать с продуктом.

По материалу курса рассматриваются: **understandability, learnability, operability, attractiveness**, а также доступность, скорость/производительность, навигация и интерфейс, плавность.

**Usability → нефункциональное тестирование.**

## 18. Accessibility Testing (A11Y)

**Accessibility testing** — проверка пригодности продукта для людей с ограниченными возможностями.

Примеры:
- вспомогательные технологии: screen readers, speech recognition, экранная клавиатура, лупа;
- использование приложения одной рукой;
- специальные настройки цветопередачи;
- понятные инструкции и руководство пользователя.

**Accessibility → нефункциональное тестирование.**

Инструменты из материала: WAVE, TAV, Accessibility Valet, Accessibility Developer Tools.

## 19. Security Testing

**Security testing** — проверка способности приложения противостоять несанкционированному доступу к данным или функциям.

Примеры угроз из материала:
- SQL Injection;
- XSS;
- перехват трафика;
- brute force.

**Security → нефункциональное тестирование.**

**OWASP Top 10** — ориентир со значимыми категориями веб-уязвимостей и рекомендациями по защите/тестированию.

## 20. Internationalization / Localization

**Internationalization testing (i18n)** — проверка готовности продукта к работе с различными языками и национальными/культурными особенностями.

**Localization testing (l10n)** — проверка корректности адаптации продукта под конкретный язык и национальные/культурные особенности.

Коротко:

`i18n → готовность к международности`

`l10n → адаптация под конкретную локаль`

Оба относятся к **нефункциональному тестированию**.

## 21. Compatibility Testing

**Compatibility testing** — проверка способности приложения работать в указанном окружении.

Подвиды из материала:

- **Configuration testing** → аппаратная платформа, ОС, сетевая инфраструктура.
- **Cross-browser testing** → разные браузеры и их версии.
- **Cross-platform testing** → разные операционные системы.

**Compatibility → нефункциональное тестирование.**

## 22. Reliability / Recoverability / Failover

**Reliability testing** → способность приложения выполнять функции в заданных условиях в течение заданного времени или количества операций.

`Reliability → стабильно работает долго?`

**Recoverability testing** → способность восстановить функции, заданный уровень производительности и данные после критической ситуации с временной/частичной потерей работоспособности.

`Recoverability → после сбоя сможет восстановиться?`

**Failover testing** → создание/эмуляция критической ситуации для проверки механизмов, предотвращающих нарушение работоспособности, производительности и повреждение данных.

`Failover → при сбое срабатывает предусмотренный механизм?`

Все три относятся к **нефункциональному тестированию**.

## 23. Performance Testing

**Performance testing** — исследование показателей скорости реакции приложения при различной по характеру и интенсивности нагрузке.

Все виды ниже относятся к **нефункциональному тестированию**.

### Load testing
Проверяем способность сохранять заданные показатели качества при допустимой нагрузке и некотором её превышении; определяем запас прочности.

`Load → допустимая нагрузка + запас`

### Scalability testing
Проверяем способность увеличивать показатели производительности в соответствии с увеличением доступных ресурсов.

`Scalability → увеличиваем ресурсы → смотрим рост производительности`

### Volume testing
Проверяем производительность при обработке больших объёмов данных.

`Volume → большой объём данных`

### Stress testing
Проверяем поведение при нагрузке, значительно превышающей расчётную, либо при недоступности значительной части необходимых ресурсов.

`Stress → сильная перегрузка`

### Concurrency testing
Проверяем поведение при большом количестве одновременно поступающих запросов, конкурирующих за ресурсы: БД, память, сеть, диск и т. д.

`Concurrency → много одновременных запросов`

### Быстрая шпаргалка

| Тип | Главная идея |
|---|---|
| Load | допустимая нагрузка и запас |
| Scalability | увеличение доступных ресурсов |
| Volume | большой объём данных |
| Stress | сильное превышение расчётной нагрузки |
| Concurrency | одновременные запросы и конкуренция за ресурсы |

## 24. Модель качества

В материале со ссылкой на **ГОСТ Р ИСО/МЭК 25010—2015** показаны характеристики качества программной продукции:

- функциональная пригодность;
- уровень производительности;
- совместимость;
- удобство использования;
- надёжность;
- защищённость;
- сопровождаемость;
- переносимость.

Для текущего этапа достаточно понимать связь характеристик с соответствующими видами нефункционального тестирования.

## Быстрая карта

```text
ТЕСТИРОВАНИЕ
│
├── Что проверяем?
│   ├── Functional
│   └── Non-functional
│
├── Как выполняем?
│   ├── Manual
│   └── Automated
│
├── Запускаем код?
│   ├── Static
│   └── Dynamic
│
├── Насколько знаем внутренности?
│   ├── Black-box
│   ├── Gray-box
│   └── White-box
│
└── На каком уровне?
    ├── Unit / Component
    ├── Integration
    ├── System
    └── Acceptance / E2E
```

> **Правило обучения:** эту шпаргалку не нужно заучивать целиком. Термины должны быть узнаваемыми и понятными; глубокое изучение начинается там, где появляется практическая задача.


## 25. Свойства качественных требований

Качественное требование должно быть понятным, реализуемым и пригодным для объективной проверки.

- **Completeness (завершённость)** — содержит всю необходимую информацию; ничего важного не оставлено в стиле «это и так понятно».
- **Atomicity (атомарность / единичность)** — описывает одну ситуацию и не объединяет несколько независимых требований.
- **Consistency (непротиворечивость / последовательность)** — не противоречит самому себе, другим требованиям и связанным документам.
- **Unambiguousness / Clearness (недвусмысленность / ясность)** — допускает однозначное объективное понимание; без расплывчатых формулировок, непонятного жаргона и неоднозначных сокращений.
- **Feasibility (выполнимость)** — технически реализуемо и укладывается в ограничения проекта по бюджету и срокам.
- **Obligatoriness + Up-to-date (обязательность и актуальность)** — требование действительно нужно проекту, имеет корректный приоритет и не устарело.
- **Traceability (прослеживаемость)** — требование можно связать с другими уровнями требований, а также с тест-планом, тест-кейсами, архитектурными решениями и т. д.
  - **Vertical traceability** — связь требований разных уровней.
  - **Horizontal traceability** — связь требования с артефактами разработки и тестирования.
- **Modifiability (модифицируемость)** — отдельные требования и набор требований можно относительно легко изменять без появления новых противоречий и потери связности.
- **Ranked for importance, stability, priority** — требования имеют понятные оценки/приоритеты по:
  - важности — насколько успех проекта зависит от реализации;
  - стабильности — насколько вероятны изменения;
  - срочности — когда нужно направить на него усилия команды.
- **Correctness (корректность)** — требование соответствует ожидаемому поведению/целям и не содержит ошибок.
- **Verifiability (проверяемость)** — можно создать объективный тест-кейс или набор тест-кейсов, однозначно показывающих соответствие реализации требованию.

> **Для текущего этапа:** свойства не нужно заучивать списком. Важно понимать общую идею: хорошее требование должно быть полным, атомарным, непротиворечивым, однозначным, реализуемым и проверяемым.


## 26. Документирование требований

### Use Case

**Use case** — сценарий взаимодействия пользователя (или пользователей) с программным продуктом для достижения конкретной цели.

На **use case diagram**:
- **Actor** — пользователь/роль, взаимодействующая с системой;
- **System** — сама система;
- **Use case** — функция/вариант использования.

Для QA use case полезен как описание пользовательского сценария, который можно проверять.

### User Story

**User story** — общее описание функции программы, написанное от имени пользователя.

Шаблон:

`As a [persona], I [want to], [so that]`

или:

> «Как [тип пользователя], я хочу [действие], чтобы [цель]».

В user story обязательно учитываются **acceptance criteria (критерии готовности)** — конкретные требования к разрабатываемой функции.

Для QA именно acceptance criteria часто становятся непосредственной основой для проверок.

### Mockup

**Mockup (макет)** — реалистичная модель приложения, показывающая, как должен выглядеть frontend.

В тестировании макет используется как ориентир для проверки:
- наличия элементов;
- их размера;
- стиля;
- поведения.

### Быстрая разница

`Use Case → сценарий взаимодействия`

`User Story → функция с точки зрения пользователя + acceptance criteria`

`Mockup → как должен выглядеть и вести себя интерфейс`

> **Для текущего этапа:** эти три понятия стоит узнавать и различать. Особенно важны **User Story + Acceptance Criteria**, потому что из них удобно переходить к тестированию конкретной функции.
